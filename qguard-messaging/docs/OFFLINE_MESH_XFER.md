# Offline Mesh, XFER and Quantum Vault

Implementation and verification record for the [offline feature guide](../../Qguard_Wiki/XFER_Decentralize_Features). The matrix distinguishes existing behavior, new code, automated checks, and work that still needs platform or hardware verification.

## HELIX Smart Connect — Windows and Android

The native Windows WinRT and Android Bluetooth adapters now share the same BLE service (`8d0d6ad1-9596-473a-bff8-6f431bb720af`), metadata format and bounded GATT stream protocol. Discovery publishes a device fingerprint, local listener port, private IPv4 hints and advertised small-message capability. Public discovery data never authenticates a device. New peers use the mutual pairing flow, and each later connection must pass the existing mutual QHCE handshake against the saved identity. Local network permission, adapter failures and scan-only support are reported from actual OS state.

Mesh tries local TCP first and uses BLE for small messages when a local IP path is unavailable. Both transports use the same hybrid ML-KEM/X25519 session and ML-DSA/Ed25519 authentication. BLE sessions reject file offers and use a 32 KiB frame cap (including JSON escaping of the 4 KiB message limit); packet streams have sequence checks, acknowledgments, lifetime, byte and connection limits. GATT polling is a compatibility path rather than a file-throughput claim. These shared protocols target Android–Android, Windows–Windows and both Windows–Android directions; physical tests for every direction remain required.

XFER uses local Wi-Fi, Ethernet or a supported hotspot with no internet requirement. Android can explicitly host a local-only hotspot; Windows can explicitly host a Wi-Fi Direct legacy access point where the driver supports it. Starting a host requires confirmation and may change the current Wi-Fi connection. Credentials appear only after an explicit reveal in the signed-in app; they are never included in public BLE metadata. **The second device currently joins through system Wi-Fi settings. Automatic authenticated hotspot credential exchange and OS client joining are not implemented.** Ordinary existing Wi-Fi/hotspot connectivity also works. Some Windows Bluetooth adapters can scan but cannot advertise, which limits Bluetooth-only inbound discovery on those adapters. [Microsoft Bluetooth support](https://learn.microsoft.com/en-us/windows/apps/develop/devices-sensors/bluetooth-dev-faq), [GATT service provider](https://learn.microsoft.com/en-us/uwp/api/windows.devices.bluetooth.genericattributeprofile.gattserviceprovider), [Android GATT](https://developer.android.com/develop/connectivity/bluetooth/ble/transfer-ble-data), [Android local-only hotspot](https://developer.android.com/reference/android/net/wifi/WifiManager).

Native picker selections are copied into account-scoped encrypted queue storage, including Android `content://` document-provider sources. Queued files no longer depend on the original file or URI after staging. Source reads and publication recheck authorization; failed staging removes partial payloads. The queue retries reachable trusted peers, retains recipient consent, and leaves explicitly paused transfers paused. Android exports verified incoming files through pending MediaStore Downloads and publishes only after a complete authorized copy. Local queue storage uses disk space for an encrypted copy of selected files.

To test without internet: verify the account while online, start local networking on both devices, enable Bluetooth and grant Nearby devices permissions, then disconnect internet access while keeping both apps unlocked. Select the peer and choose **Connect Device**. Approve on the other device, compare the codes on both screens, and confirm on both devices. Test a small Mesh message with Wi-Fi off. For files, join the same local Wi-Fi or create a temporary hotspot in Offline Settings and join it on the other device. Queue an XFER, accept the offer on the receiver, and verify the result. Repeat with sender and receiver reversed and then for each same-platform pair. Record hardware, BLE central/peripheral support and build hashes. A same-network or emulated-stream test alone does not establish physical Bluetooth interoperability.

This addition preserves the existing online transport, Vault and account controls. Cold-start offline identity enrollment, expired account credentials, multi-hop relaying, background radio service, automatic Wi-Fi client joining, cloud reconciliation and native iOS/macOS/Linux radio adapters remain separate work. The implementation must not be described as completing those capabilities.

The November 7 Smart Connect verification passed the frontend build and all 655 frontend tests. The Windows native suite passed 435 tests with the explicit storage benchmark ignored. The focused offline suite passed 30 tests with that same benchmark ignored, including an actual QHCE handshake over the fragmented GATT test stream, receipt draining after application close, live-route priority, and encrypted source recovery/cancellation. Windows GNU and Android ARM64 Rust checks passed; Android Kotlin compilation passed with JDK 21. These are automated checks rather than radio hardware evidence. ### Bluetooth link fix (November 11)

Android and Windows could find each other over Bluetooth but could not pair or deliver a Mesh message. The cause was the GATT byte stream, not discovery or the cryptography. Every packet carried 15 bytes and needed at least one radio round trip, and data sent by the accepting side needed two (a read, then an acknowledgment). One hybrid handshake is about 13 KB (ML-KEM-768 and ML-DSA-65 keys and signatures), which came to roughly 1,300 round trips, or one to two minutes on a real link. The other device shows a pairing request only after that handshake, so nothing appeared, and the request usually ran into a timeout first. The earlier tests used an in-memory stream with a 1 ms tick and never saw this.

- **Negotiated packet size.** The connecting device now negotiates the ATT MTU (Android requests 517; Windows negotiates it when the link comes up) and declares the packet size in a version 2 `OPEN` packet (`[1, 2, size]`, 20 to 512 bytes). Both ends enforce that size. A 512-byte packet carries the handshake in about 45 round trips. A version 1 `OPEN` (`[1, 1]`) still means 20-byte packets. Builds from before this change do not accept version 2, so both devices need this build for Bluetooth links.
- **Link tuning.** Android asks for the high connection priority on a data link; Windows asks for throughput-optimized connection parameters where the system supports it. Android advertises and scans in low-latency mode while discovery is on.
- **Retries.** Reads and writes are idempotent in this protocol, so the connecting side retries a failed GATT operation twice before closing the link, and retries a failed first connection once.
- **Radio contention.** A device whose hints were already read is re-read at most every 45 seconds, and never while a data link is open. Android no longer drops a peer from the list while it is connected to it.
- **Faster accept.** New Bluetooth links are collected every second instead of every four.
- **Recovery.** When Bluetooth is switched off and on again, discovery restarts by itself within about 20 seconds. It never opens a permission prompt.
- **Visible reasons.** A pairing request that fails now shows the reason the connection gave (no route, Bluetooth error, version mismatch) instead of only "the pairing connection ended".
- **Signal strength.** Nearby devices found over Bluetooth show the reported RSSI.

#### Second round, after the first device test (November 11)

The first build was installed on a real Android phone and this Windows PC. Bluetooth links now opened within seconds, and three new failures showed:

- **The phone stopped advertising.** A scan from this PC's adapter heard 24 advertisers and no Qguard service while the phone had discovery on. Many phones end a connectable advertisement when one device connects (a hint read is enough) and never resume it. Android now advertises through an advertising set, switches the same set back on when the system reports it stopped, re-checks on every connection change and status poll, and falls back to the original call on radios without advertising sets.
- **Windows was refused the stream characteristics** ("Bluetooth stream characteristic unavailable"). The by-UUID characteristic query failed against the phone although the full listing used for hint reads worked. The client now lists all characteristics, falls back to Windows' cached listing, and reports the status code.
- **"The peer identity does not match the selected fingerprint"** on the phone, and "the local peer connection closed or could not carry the frame" on the PC. The packet framing could not detect a read cut short by the radio link: the header stays valid and later bytes shift. Version 3 `OPEN` (`[1, 3, size]`) adds a size self-test. The accepting side answers the first read with a packet of exactly the agreed size; the connecting side compares what arrived, writes one full-size packet back, and reopens at a smaller size when either direction falls short (the size that arrived, or 244, 128, 64, 20 bytes). Data flows only after the test is acknowledged. The mismatch message now names both fingerprint prefixes, which tells a stale discovery entry from a damaged link.

These are fixes for what the device test showed. They are verified by unit tests and Kotlin and Rust compilation, and the Windows scanner and GATT service were exercised on this PC's adapter. The phone-to-PC pairing has not been confirmed end to end. Hardware probes (ignored tests, run with `--ignored --nocapture`): `radio_scans_and_advertises_on_this_adapter`, `unfiltered_scan_lists_advertisers_and_qguard_devices`, and `pairing_handshake_reaches_a_nearby_qguard_device`, which runs the real pairing-mode handshake from this PC against any Qguard device in range with a throwaway identity.

Files still need a local Wi-Fi, Ethernet or hotspot link. A Bluetooth link carries pairing and Mesh messages (up to 32 KiB per frame and 256 KiB per link) and rejects file offers. XFER over Bluetooth alone is not implemented.

The relay status notice ("You're offline") moved from a floating card at the bottom of the screen to a strip under the header, in the page flow, so it cannot cover buttons or the bottom navigation.

### Persistent device channel (November 12)

Physical testing on two Android phones showed that Bluetooth discovery and pairing worked but Mesh behaved as "one message, then the connection drops", replies were missing or late, and XFER screens fell back to the discovery radar. The audit traced this to how sessions were used, not to the radio or the cryptography.

**Root causes**

1. **No application session outlived one operation.** Every Mesh message dialed a new link, ran a full hybrid handshake, sent one frame, read one receipt and hung up. Over Bluetooth that is several seconds and a fresh radio link per message. A reply dialed a second link in the opposite direction. "Connected" was true only while one message was in flight.
2. **One message per peer per pass.** The send queue handed out a single pending message per peer and the queue ran on the 4-second discovery beacon, so a burst of messages trickled out one at a time, each on its own link.
3. **Competing links.** The relay exchange and the probe that ran when opening a conversation each opened another session to the same peer, competing with message delivery for the radio's few links.
4. **Bluetooth link lifetime.** The GATT stream closed after five minutes and 256 KiB regardless of activity.
5. **The view discarded its state on a slow read.** A dashboard read that took longer than 12 seconds (the transfer engine holds its store while writing a chunk) replaced the whole snapshot with an error, which unmounted the open conversation or transfer and showed the radar again.
6. **One-way discovery on hotspots.** A phone hosting a hotspot sends its UDP broadcast on its default route, so its guests never heard it while it heard them.
7. **XFER retries waited for discovery.** A queued transfer was retried at most every 30 seconds and only when the next discovery beacon ran.

**What changed**

- **Persistent channel** (`src-tauri/src/offline/channel.rs`). One long-lived, authenticated session per trusted peer, opened by either device with a `Channel` request (answered by `ChannelReady`) on an ordinary QHCE session. It stays open until the user disconnects the peer, trust is withdrawn, local networking stops, or the link is lost. Both devices send messages and receipts at any time on it; nothing reconnects per message.
- **Split session halves.** `Session::split` gives an independent reader and writer with the same per-direction keys and strictly ordered frame sequences, so a device can wait for the peer's next frame while sending its own. The cryptography is unchanged: ML-KEM-768 + X25519, ML-DSA-65 + Ed25519, HKDF-SHA3-256 and AES-256-GCM per frame.
- **Ordered delivery with receipts.** On connect and whenever a message is queued, the channel sends every pending message for that peer in the order it was written (emergency first). A message counts as delivered only when the peer's receipt is stored. A message without a receipt is resent after 20 s (Bluetooth) or 8 s (LAN); the receiver recognises a repeat by its id, returns the same receipt and raises no second alert.
- **Heartbeat and recovery.** Ping/Pong every 8 s (Bluetooth) or 4 s (LAN) measures the round trip shown in the conversation header. Silence for 30 s or 14 s ends the channel. A lost channel is dialed again after 1.5 s, then with backoff (3, 6, 12, 25, 60 s). Pending messages go out as soon as it reopens.
- **One link per pair.** When both devices dial at once, both keep the link dialed by the device with the smaller fingerprint and close the other. The larger-fingerprint device waits briefly before dialing a newly seen peer, so usually only one dial happens.
- **Relay on the channel.** The multi-hop relay exchange runs on the open channel instead of a second session.
- **Older builds.** A device that answers the channel request by closing the link twice is treated as an older build and gets one message per session, as before.
- **Bluetooth link tuning.** A GATT stream now lasts up to 12 hours and carries up to 64 MiB. The connecting side polls quickly while data flows and backs off to about 180 ms while the channel is idle, so a long-lived channel does not keep the radio at full duty.
- **XFER.** Discovery answers every device heard on the LAN directly as well as by broadcast, so discovery works both ways on hotspots. A queued transfer is retried within 6 s while a channel to the peer is open (15 s otherwise), and a failed transfer attempt nudges connected peers over their channel so the other side retries at once. File chunks keep their own sessions so a large transfer never stalls messaging. Files still need a Wi-Fi, Ethernet or hotspot link.
- **Interface.** Mesh opens a continuous conversation per device: both directions in one thread, oldest first, with per-message delivery state (Waiting for connection, Sending, Relayed, Delivered, Not delivered) taken from the stored receipts, and a header that shows what the core reports for the link (Connected with transport and round trip, Connecting, Reconnecting, In range, Not in range). The radar shows "Connected to …" or "Transfer in progress" and stops its sweep once a channel or transfer exists, and lists connected devices first. A slow dashboard read keeps the last snapshot on screen; lost authorization still clears it at once.
- **Diagnostics.** Offline Settings shows a connection log recorded by the transport and session layers: dials, authentication, channel open and close with the reason, heartbeat misses, messages queued, sent, resent, acknowledged, received and rejected, pairing steps and transfer sessions. Each entry has a millisecond timestamp, an event id and, where it applies, the first 16 hex digits of the session binding, which is identical on both devices for one session, so two phones' logs line up. Entries never contain message text, file names, keys or full fingerprints, and are kept in memory only (`offline_link_events`).

**Verification so far.** 86 offline Rust tests pass, including two-way concurrent messaging over split session halves through the Bluetooth packet layer, ordered retrieval of 20 queued messages, receipt and emergency ordering, the crossing-dial rule and the registry's link view. The frontend passes 739 of 740 tests (the remaining failure is the unrelated `ai-assistant.test.ts`). The conversation layout was checked in `tools/mesh-conversation-preview.html` at 375 × 812 (Android skin, light and dark) and desktop width. **None of this has been run on two physical devices yet**; the acceptance tests in the audit (20 messages each way, disconnect and recovery, multiple consecutive transfers, Wi-Fi interruption) need the owner's phones.

## Architecture and rollout

The existing Tauri process owns account context, key material, sockets and storage. The React shell calls typed Rust commands and refreshes from Rust events. The new `src-tauri/src/offline/` modules separate the command boundary, native account verification, account profile, LAN discovery, network lifecycle, authenticated session, wire records, messaging, and transfer engine. Local records use bounded encrypted documents and atomic checkpoints. This implementation requires no new Supabase migration and does not introduce a local relational database, its indexes, or cloud synchronization for Mesh or XFER.

Before opening local networking or records, the native process verifies the current Supabase user token with the build-pinned project's HTTPS `/auth/v1/user` endpoint. The verifier uses TLS 1.3, disables proxies and redirects, and checks the returned user ID against the active account. A process-memory grant binds that account to a digest of the exact verified token and its expiration. A warm app can operate offline under the same token until expiry. A new or refreshed token needs verification. A running network can wait up to 15 seconds for verification of a renewed token for the same account. A restart clears the grant. Android additionally requires the enrolled app unlock. Cold starts, expired tokens and an unreachable sign-in service use the device-bound offline enrollment below.

### Offline sign-in (device-bound enrollment)

Each successful online verification (`principal.verify`) writes or renews an `offline-enrollment` record for that account, sealed under the device storage key like the other offline records. The record holds the account ID, the normalized email, the verification time, the failed-attempt count, the last subscription row seen online (used only for the offline UI paywall verdict, like the online one), and on desktop a password verifier. It never holds the password, a Supabase token, or anything that authorizes an online service.

- **Window.** Offline access lasts 30 days from the last online verification. A clock set more than five minutes before the verification time is refused. Every online sign-in renews the window and clears failed attempts.
- **Desktop.** After an online password sign-in (and after MFA when the account uses it), the app sends the password once to `offline_enroll_password`, which re-verifies the online session first. The verifier is a stretched key derived with the same KDF as the workspace passcodes (Argon2id 64 MiB, three passes; PBKDF2-SHA512 in FIPS mode) under a random salt, then HKDF-SHA3-256 with a domain-separated label. When the sign-in service cannot be reached (a network failure, a timeout, or a retryable 5xx), `offline_sign_in` compares the entered password in constant time. Five wrong passwords lock offline sign-in until the next online sign-in; the command is also rate-limited per email. Known limits: a password changed elsewhere keeps working offline on this computer until its next online sign-in (the record is readable only inside the same Windows account, through its device storage key), and accounts that sign in with a mobile number have no password, so on desktop they need internet.
- **Android.** No password verifier is stored. The app-entry PIN, pattern or biometric unlock is the local proof: `offline_resume_unlocked` succeeds only while the app lock is unlocked for that same account. The stored session's tokens stay in memory, and the app retries them every 30 seconds and on the `online` event, returning online by itself. A server rejection of the stored session ends offline mode and asks for a full sign-in.
- **Scope.** A successful offline sign-in sets a process-memory offline grant that authorizes only the offline module (Mesh, XFER, transfer history and offline settings). It is never online proof. `offline_store_entitlement` and `offline_enroll_password` require a live online verification. The grant never serves a different account than the one signed in online, and an online-verified session always takes precedence. `offline_sign_out` stops local networking and drops only the offline grant. Online sign-out clears both grants.
- **Isolation from online features.** In offline mode the React shell mounts only the offline workspaces. Secure Chat, Calls, Quantum Vault, billing, realtime streams and the relay courier stay unmounted, because they need an online session that does not exist offline. Online, Mesh and XFER keep working beside every online feature exactly as before, and the offline grant changes nothing while an online session is verified.
- **Turning it off.** Offline Settings shows whether offline sign-in is on and until when. "Turn off offline sign-in" deletes the enrollment for that account on that device (`offline_forget_device`). A device-identity reset after a lost storage key sets the record aside with the other sealed offline documents.

LAN operation requires IP reachability on a trusted private network, which may be Ethernet, existing Wi-Fi or a user-created hotspot. Guest Wi-Fi client isolation and firewalls can block peer traffic even when both devices show a Wi-Fi connection. Start networking on both devices and use mutual pairing to trust a peer. If broadcast discovery is unavailable, use a private network that permits peer-to-peer discovery or supported Bluetooth discovery.

Automatic local-network activation and transport selection are distinct. An opted-in recovery policy can start LAN listening when the Secure Chat relay is unavailable and stop automatic discovery after the relay recovers and active transfers end. A manually started listener stays enabled until stopped. Both manual start and opted-in automatic recovery start native Bluetooth discovery when OS permissions are already granted; automatic recovery never opens a permission prompt. Smart Connect prioritizes live LAN routes over manual and Bluetooth IP hints, authenticates the selected peer, and falls back to BLE for small Mesh messages. Files wait for a usable local IP path. Automatic client Wi-Fi joining and measured link-quality ranking remain future work.

## Discovery and application frames

Discovery sends the existing fixed-size IPv4 UDP announcement on port 39837 alongside an optional metadata announcement. The original fields are `QGUARD-LAN/1\0`, a 32-byte device fingerprint and a two-byte unsigned big-endian TCP port. The `QGUARD-LAN/2\0` variant adds a platform identifier and a bounded UTF-8 device label. Windows and Android can also report discovery metadata through an optional BLE GATT characteristic. These names and platforms are discovery hints until the pairing session authenticates them. Receivers take the LAN address from the packet source, reject malformed datagrams and self-announcements, and expire old observations.

Discovery is unauthenticated presence data. It reveals the stable device fingerprint and listener port to others on the broadcast segment. A peer can spoof an announcement or flood the discovery table. Authorization requires a pinned fingerprint and proof of the corresponding identity inside the secure TCP session. Stop local networking when peer discovery is no longer needed. Previously saved manual endpoints remain usable after authenticating the saved identity.

Inside the authenticated session, application payloads start with one type byte. Type 0 contains a strict JSON control object tagged with `type` and optional `value`, limited to 1 MiB including the type byte. Type 1 carries the bytes of a single transfer chunk. Out-of-order or unexpected controls fail the operation.

The Rust core pushes a payloadless `offline:changed` event through Tauri when local state changes. Each dashboard reads networking status and its page records through one `offline_dashboard_snapshot` IPC command. Native authentication selects the account and checks it again before returning the result. The hook coalesces events, refreshes when the window regains focus, and uses a periodic read to recover missed events. Dashboard snapshots stay inside the app's IPC boundary.

### Authenticated session v1

The six-byte handshake header is ASCII `QGLN` followed by version 1 and suite 1, each one byte. One type byte follows that header. The suite fixes X25519, ML-KEM-768, Ed25519, ML-DSA-65, HKDF-SHA3-256 and AES-256-GCM. Unsupported versions, suites and provider modes fail closed. The QHCE reference provider supplies the new suite. Builds using wolfCrypt or FIPS approved mode reject the local networking suite. Existing Vault recovery and sharing keep their own ML-KEM-1024 envelope and do not use this TCP session format.

1. `Hello` (type 1) contains the initiator's Ed25519 public key, ML-DSA-65 public key, 32 random bytes, ephemeral X25519 public key and ephemeral ML-KEM-768 public key.
2. `Reply` (type 2) contains the same identity, random and X25519 fields from the responder, then its ML-KEM-768 encapsulation ciphertext, Ed25519 signature and ML-DSA-65 signature. Both signatures cover the same domain-separated digest of `Hello` and the unsigned `Reply`.
3. `Finish` (type 3) contains the initiator's two signatures over the domain-separated digest of `Hello` and the signed `Reply`. Each side verifies its peer against the independently pinned fingerprint. That fingerprint is a domain-separated SHA3-256 digest of the combined public identity bytes. The identity keys are sealed under the existing account's device storage protection.
4. The session ID is a domain-separated digest of the complete signed exchange. HKDF-SHA3-256 uses it as salt and the fixed-width concatenation of the ML-KEM and X25519 shared secrets as input. Distinct direction labels derive the two traffic secrets. Invalid or non-contributory input terminates the handshake. Each party confirms possession with an encrypted, role-specific session confirmation before accepting application records.

All protocol digests in the handshake and frame layer hash the domain label followed by each field's eight-byte big-endian length and bytes. The source specifies the literal labels and serialization. The encrypted frame is a four-byte big-endian length followed by the eight-byte big-endian sequence, 12-byte nonce, ciphertext and 16-byte tag. The session derives a fresh key for each direction and sequence through HKDF-SHA3-256. The associated data binds the session ID and expected sequence. Confirmation consumes sequence zero. Receivers enforce strict sequence order and a payload maximum of one 4 MiB chunk plus its type byte. The handshake deadline is 20 seconds and each encrypted frame has a 30-second I/O deadline. Authenticated transfer checks can send bounded progress keepalives during expensive storage verification.

The secret ordering follows the published X25519MLKEM768 TLS group. The Qguard session uses its own transcript, signatures, key confirmation and framing. The construction requires independent review and protocol vectors before production security claims. [Session implementation](../src-tauri/src/offline/session.rs), [NIST KEM guidance](https://csrc.nist.gov/pubs/sp/800/227/final), [TLS 1.3 hybrid group specification](https://datatracker.ietf.org/doc/html/rfc10024).

### Mutual device pairing

New trust records require a pairing-only session with a separately signed handshake type. These sessions accept pairing frames only. Both users approve the connection and compare a 64-bit code derived from the signed session transcript, pairing identifier, both authenticated device descriptions, requested capabilities and fresh nonce commitments. Both local confirmations are required before either device can save a trusted identity. Trust records are encrypted per account. Pairing does not accept an XFER offer or authorize file access.

Pairing protocol version 2 (November 9) scopes trust to the requested connection type. A request asks for Mesh, XFER, or both, and each device stores only the capabilities both users approved, even though both devices advertise both. Mesh sends and receives require Mesh; new XFER offers, receiver pulls and uploads require XFER. Controls for an existing transfer (pause, stop, cancel, receipts) stay available so either side can settle it. A later pairing of the same identity key can add a capability and keeps the original pairing date. Fingerprints pinned before scoped pairing keep their original access. Version 1 peers fail closed before any prompt, so both devices need the same build.

After both users confirm the code, the Commit and Committed frames carry each account's display name over the verified session. The name is never in discovery data, Bluetooth metadata or the incoming request, and it is a label rather than an identifier. The dashboard and trusted-device list show it with the device name.

The app displays incoming requests across its unlocked screens. On desktop, a Rust-side notification also announces an incoming request, a code that is ready to compare, an XFER offer, a verified completion, or a transfer failure that needs action, when the Qguard window is not in front. Notifications carry device names and file counts and sizes, never file names, message text or fingerprints. The notification plugin is registered only for desktop and only Rust raises notifications. Android locks Qguard when it leaves the foreground. Unless the user turned on background Mesh (see Background Mesh on Android), that suspends local networking; with it on, Mesh messages still arrive and raise a private Android notification, while pairing requests and XFER offers are refused until Qguard is unlocked. The current verified account session is still required, and is separate from the offline peer exchange. Windows and Android support LAN and compatible BLE adapters. The shared macOS and Linux code uses LAN; physical cross-platform validation remains required.

### Mesh delivery

The sender writes a UUID, sender fingerprint, recipients, message, optional group label, emergency flag, creation time and expiration to the account's sealed local ledger. For a group, it sends one `message` control to each named recipient over that recipient's authenticated session. Each control contains the fingerprint of that recipient. The group label is presentation metadata. It confers no independent membership rights and does not create a relay route.

The receiver verifies that the sender is the authenticated peer, that the recipient is the current local identity, and that the envelope is within its permitted lifetime. It saves before returning a `receipt` containing the message UUID and both fingerprints. An identical retry receives the same receipt. Reusing the same sender and UUID with altered content is rejected. The outgoing record becomes delivered after all intended peers acknowledge it. Messages to unavailable peers remain on the sender until a direct connection succeeds or the message expires.

The receiver records when each message arrived and when the user opened or dismissed it, inside the same sealed ledger. A newly stored message (never a retried delivery) raises `offline:changed`, and the app shows an in-app notice on every screen with the sender, a short preview, the session suite and **Open** and **Reply**. Opening or dismissing it marks the message read, so it does not return after a restart. While the Qguard desktop window is not in front, a desktop notification names the sender only and never carries message text. The notice reads unread messages through `offline_mesh_monitor`, which is scoped to the verified account. A directly delivered Mesh message travels only on the authenticated session (a relayed copy is sealed separately, see Multi-hop relay): ML-KEM-768 + X25519 key establishment, ML-DSA-65 + Ed25519 device signatures, and AES-256-GCM per-frame encryption, over LAN or BLE.

Each message body is limited to 4 KiB and each group label to 100 bytes. The sender supports up to 16 recipients per message. The sealed ledger is bounded to 1,024 records, 256 pending and 8 MiB. Message expiry is between one minute and seven days. The scheduler prioritizes emergency messages, then uses creation time and UUID. This prioritization does not imply extended radio range, emergency services contact or delivery guarantees.

### Multi-hop relay (store, carry and forward)

A message that cannot be delivered directly within 20 seconds is also sealed into a relay envelope and handed to reachable devices that are paired for Mesh. Those devices carry it and hand it on, up to four relays, until it reaches the recipient. The direct path stays active; whichever copy arrives first is stored and later copies are recognised by message ID and dropped.

- **End-to-end sealing.** The sender derives a one-time key from X25519 and ML-KEM-768 against the recipient's static relay key, combined with HKDF-SHA3-256 over both shares and the transcript, and encrypts with AES-256-GCM. Inside the ciphertext the sender signs the payload with its pinned Ed25519 + ML-DSA-65 device identity. The recipient accepts an envelope only from a device it paired with for Mesh. The envelope ID, addressing tag and times are authenticated data. The hop counter is not, because relays decrement it.
- **What a relay sees.** An opaque per-envelope tag (SHA3-256 over the recipient fingerprint and the envelope ID), sizes and times. It never sees the sender, the recipient or any text, and it cannot link two envelopes to the same recipient.
- **Relay keys.** Each device keeps a static X25519 + ML-KEM-768 relay key pair in a sealed document and sends the public half to a paired peer on the authenticated session (`relay` / `relayAck` controls). A sender can therefore relay only to recipients it has paired with and met once since this feature was installed. Static recipient keys mean relay envelopes do not have forward secrecy against a later compromise of the recipient device; direct sessions keep their ephemeral key exchange.
- **Delivery receipts.** The recipient seals its signed receipt back to the sender the same way. A message is marked delivered only when that receipt arrives, directly or through relays; until then the sender shows "Relayed, awaiting delivery". A relay can never confirm delivery.
- **Bounds.** Four hops; envelope lifetime equal to the message lifetime (at most 7 days); 256 carried envelopes in total and 64 from any one peer; 512 own envelopes; duplicate suppression by envelope ID (4,096 remembered IDs); an envelope is never returned to the device it came from and is offered to each device once. One envelope per Bluetooth exchange and 16 per LAN exchange. With nothing to hand over, a device asks each reachable peer once a minute.
- **Trust model.** Relays are devices the user paired with for Mesh, not strangers: this is a friend-to-friend mesh. A crowd of unpaired Qguard users does not relay for each other. "Relay messages for trusted devices" in Offline Settings is on by default; turning it off drops what the device was carrying, and its own messages can still travel through others.
- **Not covered.** Files (XFER) are never relayed. There is no routing table or path selection; forwarding is bounded flooding among trusted devices.

### Background Mesh on Android

By default Android locks Qguard when it leaves the screen and local networking stops. With "Keep Mesh running in the background" on (Offline Settings; off by default), a visible `connectedDevice` foreground service (`HelixMeshService.kt`) keeps the process alive, holding a partial wake lock and a Wi-Fi multicast lock only while it runs. The network that the user started while unlocked then keeps serving that same account after the app lock engages:

- Mesh messages are received, stored in the sealed ledger, acknowledged and relayed while locked.
- A new message raises a private Android notification that names the trusted device but never carries text. Its lock-screen version says only that there is new encrypted activity.
- Pairing a device, reading messages, sending, changing settings and every XFER file operation still require an unlocked Qguard. A transfer in progress pauses when the app locks.
- The service does not restart by itself after the process is killed, a reboot or a force stop: opening and unlocking Qguard starts it again. Battery optimisation on some phones can still stop it, and Android's Doze mode can delay Wi-Fi discovery; Bluetooth links are less affected. None of this has been measured on physical devices yet.
- Google Play requires a declaration for the `connectedDevice` foreground-service type in the Play Console before release.

Desktop needs no service: Mesh already runs while the window is minimised.

### XFER state machine

1. The sender opens a session to the recipient's pinned identity and sends `offer`. The manifest binds a transfer ID, sender, recipient, relative file names, byte lengths, chunk counts, digests, creation and expiry. A subsequent offer with the same ID must match the stored manifest and identities.
2. The receiver responds with `awaitingConsent` or `declined`, or returns missing chunk positions for a previously accepted transfer. Consent is recorded separately from discovery and pairing. A receiver can request a fresh offer with `requestSend` for the same transfer ID. Retrying uses the same manifest with a fresh authenticated connection. An explicit local pause is persisted separately from an interruption. Resuming a paused transfer requires a local action.
3. For each missing file range, the receiver requests one ordered `requestChunk` at a time. The sender returns a chunk frame. The receiver checks the expected length and ordering, seals the bytes into private staging, records the verified checkpoint, and returns the matching `chunkAck`. The sender's progress reflects the authenticated recipient's acknowledged bytes. Receiver progress reflects its own persisted checkpoint.
4. The receiver verifies each completed file against the manifest digest before sending `complete` with the transfer ID. Final integrity verification and saving the received files are separate actions. The initial protocol uses 4 MiB chunks and caps a manifest at 128 files and 32 GiB of payload.

The sender stores its source paths and per-chunk SHA3-256 digests in an encrypted checkpoint. Retrying after an application restart requires the same source files. Each source chunk is rechecked against the original digest before transmission. The receiver reopens and validates its authenticated chunk prefix before advertising missing chunks. Each staging write derives an independent AES-256-GCM key using HKDF-SHA3-256 with a random 256-bit salt. The transfer ID, file and chunk positions, and checkpoint role are authenticated as associated data. Staging and history are bounded, including a 64 GiB reserved incoming staging quota, 16 pending offers and 128 history records. Transfer payloads expire after 24 hours.

Verified bytes remain in encrypted staging until a destination action. Consent can select automatic import into the unlocked Quantum Vault after verification. If automatic import is interrupted, the user can retry the remaining files from XFER while encrypted staging is available. Vault import streams verified chunks directly into the existing storage pipeline. It rechecks the byte count, plaintext digest and active Vault key before committing the encrypted object. A Vault import follows the Vault's existing user-configured backup setting.

A local export stages plaintext inside private application storage and publishes it without replacing an existing file. The destination must support no-overwrite publication on the same drive as Qguard storage. After a crash, the next account transfer recovery clears abandoned export staging. Sender paths and destination locations are private checkpoint data. Only validated relative names are sent to the peer. Rust issues short-lived, single-use, account-bound tokens for native picker selections. The WebView passes these tokens when sending. The sender pins canonical paths, excludes Windows reparse points and checks the opened file against the selected inode on Unix. Desktop folder manifests preserve the relative paths of their files. Android XFER accepts native filesystem selections and `content://` document-provider selections through the native streaming bridge. Files are copied into encrypted queue storage before a visible outgoing record is committed.

This protocol is internal to the Qguard builds that use this version. Future changes to the suite or framing require an explicit new version and interoperation tests.

### Live transfer dashboard evidence

The XFER dashboard shows only values the transfer engine reports. Progress counts verified bytes and stays at 99 percent until the receiver's SHA3-256 receipt arrives. Throughput samples are the engine's own measurements. When no verified checkpoint arrives for two measurement windows while payload is moving, the engine records measured zero throughput each second, so the graph shows the stall. A pause or interruption ends the run, and the graph draws that gap as a dashed break instead of a slope. Final integrity verification is not sampled as a stall.

Each transfer record keeps the first 64 bits of the authenticated session binding, the SHA3-256 digest of the signed hybrid handshake. Both devices derive it from the same session, so the sender and receiver dashboards show the same session ID for the same transfer. It reveals no key material. The transfer details show each file's manifest SHA3-256 digest. The completion receipt lists the sender, receiver, size, duration, integrity result, suite and completion time. An outgoing transfer that was declined, cancelled, expired or failed offers **Send again**. That opens a fresh, consented offer to the same verified device, because the sender erases its encrypted copy when a transfer ends.

Automated wire evidence (`offline::session::tests`) relays a session through a recording proxy. It checks the ML-KEM-768 encapsulation key and ciphertext sizes, the Ed25519 and ML-DSA-65 identity and signature sizes in the handshake, that a full 4 MiB chunk frame carries exactly the 8-byte sequence, 12-byte nonce, ciphertext of the plaintext length and 16-byte tag, and that no plaintext fragment crosses the wire. A second test flips one ciphertext bit and confirms that AES-256-GCM authentication rejects the frame and every later frame on that session. These are automated checks of this implementation, not a FIPS validation or an independent protocol review.

## Release checklist

- [ ] Run frontend typecheck/build, Rust checks and full tests, and native builds from a clean checkout on supported release toolchains.
- [ ] Exercise Secure Chat, account/device restore, app and workspace locks, Vault, and billing through their ordinary entry points.
- [ ] Verify offline discovery and pairing on physically separate devices with internet access disabled. Include permission denial, guest-network isolation and reconnect.
- [ ] Verify consent and trust revocation, replay, malformed frames, altered manifests, corrupt chunks, disk-full and interrupted publication. Test recovery after app shutdown and reboot.
- [ ] Run the requested Android, Windows, iOS, macOS and Linux pairings where supported, including Vault sharing, and record devices, build IDs and permission configuration.
- [ ] Measure 100 MB, 500 MB, 1 GB, 5 GB and 10 GB on hardware. Record link type, bytes, wall time, throughput, CPU, peak memory, disk I/O, crypto overhead, final verification and resume time. Record matching chunk sizes and operating conditions.
- [ ] Verify the cryptographic and storage boundaries independently, run dependency and license audits, and resolve critical findings before release claims.
