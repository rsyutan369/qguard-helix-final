# FIPS 140-3 in QGuard Messaging

**Status (2026-11-03):** the app's cryptography runs behind one boundary
(`src-tauri/src/crypto/provider/`) that can be backed by wolfCrypt. The
release builds still use the bundled RustCrypto / dalek / PQClean backend,
which is **not a CMVP-validated module**. Nothing in the app may be described
as "FIPS validated", "FIPS certified" or "FIPS compliant" until a build links
a validated module and the certificate covers what the app uses. What can be
said today: *built on NIST-approved algorithms (FIPS 197, 202, 203, 204,
186-5; SP 800-38D, 800-56C, 800-132)*.

HMAC-SHA3-256 and the DRBG. The post-quantum algorithms become validated only
when wolfSSL's "wolfCrypt Post Quantum" module receives its certificate.

## 2. Architecture

```
app code ──► crypto::provider ──► backend
              (the boundary)      ├─ rustcrypto.rs   default; RustCrypto, dalek, PQClean
                                  └─ wolfcrypt.rs    --features wolfcrypt
                                       └─ wolfcrypt/qg_wolfcrypt.c ──► wolfCrypt
```

* Nothing outside `crypto/provider/` names a cryptographic crate (`aes_gcm`,
  `sha2`, `sha3`, `hmac`, `hkdf`, `x25519_dalek`, `ed25519_dalek`,
  `pqcrypto_*`, `rand::OsRng`). Argon2id is the one function outside both
  backends (wolfCrypt has none); it is marked non-approved.
* AES-GCM encryption nonces are generated inside the module and returned
  (IG C.H); callers cannot choose one. In a wolfCrypt FIPS build the
  external-IV encrypt is not even an approved service.
* Known-answer and pairwise self-tests (`selftest.rs`) run at launch on a
  background thread and before the first keyed operation. A failure puts the
  boundary in an error state: every keyed operation refuses. Vectors:
  FIPS 180-4 / 202, GCM spec test case 16, RFC 7748, RFC 8032, and FIPS 203/204
  vectors that OpenSSL 3.5, wolfCrypt 5.9.4 and PQClean all agree on (OpenSSL
  and wolfCrypt derive identical ML-KEM-1024, ML-DSA-65 and ML-DSA-87 public
  keys from the same seeds; wolfCrypt and PQClean decapsulate OpenSSL's
  ciphertext and accept its signatures).
* The WebView no longer does cryptography in the apps: chat attachments
  (AES-256-GCM), attachment and audit digests, recovery-code hashes, the
  device-link proof (HMAC-SHA3-256) and the legacy privacy-screen verifier
  all go to the module (`src/lib/core-crypto.ts`, `commands::crypto_module`).
  **Exception:** call audio/video frames are still encrypted by WebCrypto
  inside WebRTC encoded transforms — per frame, where a round trip to the
  core is not possible. Settings lists this as outside the module.

## 3. FIPS approved mode

Settings → Security → *FIPS 140-3 cryptographic module*. Per device, off by
default; `QGUARD_FIPS_APPROVED_MODE=1/0` overrides it; a build with
`--features fips-approved-mode` cannot leave it.

| | Standard mode | Approved mode |
|---|---|---|
| Password / PIN stretch | Argon2id (64 MiB, t=3) | PBKDF2-HMAC-SHA-512, 600,000 iterations, 128-bit salt |
| Quantum Vault credential | password ≥ 12, PIN 6–12 digits or 4 × 4 pattern ≥ 6 dots | **password ≥ 14 characters** |
| Hidden vaults (pattern + device key, Argon2id) | available | not created; existing ones still open |
| Portable identity export | v1.2 (Argon2id) | v1.3 (PBKDF2-SHA-512 → HKDF-SHA3-256) |

* Every stored credential records its KDF, so both kinds always open. On the
  next successful unlock a credential is re-sealed under the current mode's
  KDF (workspace vault/chat, app lock, privacy screen); duress PINs and
  social-recovery setups keep theirs until they are set again.
* **A Quantum Vault PIN or pattern is never moved to PBKDF2.** Without
  Argon2id's memory cost a short secret in front of the vault key becomes
  easier to guess offline, so it stays Argon2id and is reported as not meeting
  approved mode until a 14+ character password is used instead. For the same
  reason no new pattern or hidden vault can be set up in approved mode, and a
  hidden vault cannot be recovered with its 12-word phrase there either (the
  recovery sets a new pattern). The phrase itself is 128 random bits through
  HKDF-SHA3-256 with no password stretching.
* Approved mode cannot be switched on while a self-test has failed.
* X25519 stays in the hybrid as the second secret next to ML-KEM-1024; the
  combiner puts the ML-KEM (approved) secret first, as SP 800-56C r2 allows.

## 4. Building with wolfCrypt

```powershell
# development: open-source wolfSSL (GPLv3 — never distribute such a build)
$env:WOLFSSL_DIR = "<wolfssl source tree, e.g. v5.9.4-stable>"
cargo build --features wolfcrypt

# validated: wolfSSL's commercially licensed FIPS 140-3 package, built
# exactly as its Security Policy / User Guide prescribe
$env:WOLFSSL_LIB_DIR = "<dir with the built library>"
$env:WOLFSSL_INCLUDE_DIR = "<its headers + the user_settings.h it was built with>"
cargo build --features "wolfcrypt fips-approved-mode"
```

`wolfcrypt/user_settings.h` is for the development build only (portable C, no
ARMv8 crypto opcodes, small stack). The FIPS package dictates its own
configuration, build and in-core integrity procedure.

Verified on 2026-11-03: the whole Rust suite passes on both backends (362
tests default, 367 with wolfCrypt, including cross-backend interop: keys and
signatures made by either backend are accepted by the other, so devices need
no re-keying to switch). wolfCrypt and the shim cross-compile for Android
arm64 with NDK r27, and the objects contain no ARMv8.2 SHA-3 or ARMv8
crypto-extension opcodes. Not done: an APK linked with wolfCrypt, a run on a
device, or any build from the FIPS package.

## 5. What remains outside this repository

1. **License** — wolfSSL's FIPS 140-3 package is commercial; the open-source
   tree is GPLv3 and this app is proprietary.
2. **The post-quantum certificate** — until "wolfCrypt Post Quantum" (or
   another module covering ML-KEM, ML-DSA, EdDSA, HKDF and PBKDF2 on
   Windows and Android) is validated, those algorithms run outside any
   validated boundary even in a wolfCrypt FIPS build. Settings shows exactly
   which rows are inside it.
3. **Platforms** — the certificate lists specific devices (e.g. Galaxy S23,
   i7-1255U). Other phones and PCs need the vendor's or a lab's confirmation
   (porting / vendor affirmation).
4. **HKDF hash** — the app's KDF is HKDF-SHA3-256. If the eventual module's
   HKDF is SHA-2 only, the key schedule needs a versioned move to
   HKDF-SHA-384/512.
5. **Call media** — needs a native media path to enter the module.
6. **Independent review** — an accredited lab's integration review and an
   external cryptography audit of the protocol design.
