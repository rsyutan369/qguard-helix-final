# Qguard Helix telemetry and operations audit — 16 November 2026

**Verdict:** All 17 dashboard routes are registered and have tenant data readers and a server-sent events (SSE) path. They are not ready to serve as the definitive record of current asset posture, migration completion, or collector health. Several dashboards agree because they share the same calculation; that agreement does not substantiate the calculation. The most urgent issues are account changes with in-flight requests, untrustworthy freshness indicators, and security decisions based on evidence that does not belong to the asset, listener, job, or time window shown.

**Scope:** Read-only review of the current working tree: route registration, page components, hooks, REST and SSE contracts, Realtime subscriptions, source queries, ingestion, evidence classification, cross-module joins, and displayed counts. Source references below are paths from the repository root. P1 means fix before relying on the affected output for an operational/security decision; P2 means fix to make the output complete, interpretable, or consistent. No application code, schema, live telemetry, or migration records were changed.

- **P1 — Account changes can restore data from the previous account.** TLS/PKI, Trust Fabric and Encryption Monitoring clear snapshots in an effect after the account changes, but an older request can still resolve and repopulate the view. Trust detail and pagination state also lack a user key. Runtime Telemetry does not scope every write or reset the previous snapshot by account. The shared live hook guards late writes but still exposes its previously stored model until its effect resets it. This is a client lifetime risk on an in-place authenticated identity change; no server-side cross-tenant disclosure was observed. Key the dashboard and request state by authenticated account, cancel old snapshots, streams, detail reads and timers, and reject any obsolete response. (`src/hooks/use-trust-fabric.ts:302,425,476,557`; `src/hooks/use-tls-pki.ts:225,350`; `src/hooks/use-encryption-monitoring.ts:129,248`; `src/hooks/use-runtime-telemetry.ts:70,130`; `src/hooks/use-live-resource.ts:141,162,185`.)
- **P1 — Repository database permissions do not protect machine evidence from interactive edits.** If applied as written, the Data API grant script plus owner-scoped `FOR ALL` policies let an authenticated account modify its own runtime events, inventory, and migration jobs outside the collector and workflow checks. This is a data integrity boundary, distinct from tenant isolation. Deployed permissions were not verified. Inventory the legitimate write paths, restrict authoritative records to trusted producers, and allowlist user-editable fields or operations separately. (`supabase/data-api-grants.sql:62`; `supabase/dashboard-schema.sql:477,593,1491`.)
- **P1 — “Live” can outlast usable data.** `useLiveResource` waits indefinitely after the first frame if the connection never closes; its initial timer does not provide ongoing fallback. Application error frames do not clear stream status. TLS, Trust, Encryption and Runtime Telemetry also mark a successful HTTP connection live before a usable snapshot and do not consistently degrade on stream error. Several “Reconnect” controls only run a REST refresh. Unchanged frames can advance freshness on a cached result. Require `text/event-stream`, a successful first snapshot and a recurring snapshot deadline. On failure, show stale/unavailable, poll REST while reconnecting, and expose source `observedAt`/`lastSuccessfulReadAt` separately from transport `checkedAt`. (`src/hooks/use-live-resource.ts:203,210,221,248`; `src/api-server/live-snapshot-stream.ts:104`; `src/hooks/use-tls-pki.ts:292,374`; `src/hooks/use-trust-fabric.ts:373,390,448`; `src/hooks/use-encryption-monitoring.ts:191,270`; `src/hooks/use-runtime-telemetry.ts:161,178`.)
- **P1 — Runtime ingestion and asset evidence can diverge.** The direct agent ingestion path persists observations before resolving and publishing canonical asset evidence; failures after the first write can leave rows with missing or different asset linkage. A missing runtime table can return a successful accepted count with zero inserts. Scan evidence is also mirrored into the runtime event table, and the runtime path mirrors back into evidence. Static manifest, configuration or certificate discovery can consequently be presented as observed runtime crypto, and copies can be counted as independent sources. Bind canonical assets before publishing, retain evidence kind and observation lineage, and acknowledge only durable committed data with retry and reconciliation. (`src/api-server/agent-scanner.ts:1294,1335,1375,1432,2050,2084,5273,5305`.)
- **P1 — Weak protocol evidence is promoted to a confirmed downgrade.** Agent normalization can flag a weak protocol alone; Runtime Crypto Intelligence interprets the flag as attempted PQC/hybrid negotiation followed by classical fallback. TLS and Drift consume the same flag. Separate “weak protocol observed,” “classical negotiated,” and “verified fallback”; require attempt and negotiated-result evidence for the last claim. (`src/api-server/agent-scanner.ts:1255`; `src/lib/runtime-crypto/runtime-intelligence.ts:811`; `src/lib/tls-pki/intelligence.ts:365`; `src/api-server/drift-detection.ts:64`.)
- **P2 — A successful but incomplete read often looks complete.** The shared ledger infers truncation from the requested cap and rows returned, sometimes after filtering. Several builders pass `limit: null` despite their query limits. A database row cap lower than the application limit can silently undercount; the deployed cap was not verified. Some collectors also map read errors to zero rows. Use stable pagination and explicit counts/completeness, carry upstream source health to the displayed KPI, and distinguish measured zero, no evidence, partial, and unavailable. (`src/api-server/source-ledger.ts:57`; `src/api-server/tls-pki.ts:122`; `src/api-server/encryption-monitoring.ts:93`; `src/api-server/trust-fabric.ts:137,264`; `src/api-server/runtime-telemetry.ts:41,133`.)
- **P2 — Legacy Runtime Crypto routes do not share the same plan check.** The dashboard router still mounts older authenticated REST and stream handlers; the Pro subscription prefixes cover the newer route family. The older handlers are authenticated, so this is an entitlement inconsistency. Retire the legacy handlers or apply the same entitlement policy to both. (`src/api-server/dashboard.ts:3495,3760`; `src/api-server/index.ts:781`; `src/api-server/subscription-guard.ts:82,188`.)

## Verified and unverified boundaries

- **Local HTTP:** Vite served the app shell with HTTP 200 for all 17 URLs and `/api/v1/health` returned 200 JSON. All 16 distinct snapshot endpoints and their 16 `/stream` endpoints returned 401 JSON to unauthenticated GETs. Timeline and PQC Orchestration share one endpoint. The route declarations and API mounts were checked in `src/App.tsx` and `src/api-server/index.ts`. These checks confirm the shell and anonymous rejection, not signed-in rendering, plan entitlements, or tenant isolation.
- **Build:** `npm.cmd run lint` (`tsc --noEmit`) passed. A Vite production client build to a temporary directory passed with CSS and bundle warnings. The unrelated agent release prebuild was not run.
- **Offline model checks passed:** Drift, Migration Orchestrator, Crypto Agility, TLS/PKI/Trust Integrity, Telemetry Correlation, Runtime Crypto Intelligence, Quantum Risk, and Trust Workflow Graph. These test their existing assertions and do not negate the reproduced failures.
- **Offline rendering and SSE:** 41 server-rendered cases across the seven Intelligence and Operations routes passed with auth and data hooks stubbed. The Intelligence and Operations contract suite passed its route/header assertions and in-process SSE full, unchanged, changed and disconnect framing. No real tenant events were involved.
- **Confirmed with new no-write cases using the actual builders:** false runtime migration confirmation; drift with incomparable scans and future jobs; duplicate-source correlation coverage; risk coverage with no evidence; job validation leaking to another job on the same asset; inflated handshakes, merged TLS listeners and erased trend activity; serial collisions and future certificate validity; false trust measurements, incomplete-chain preview undercount; cloud encryption inferred from ML-KEM; and contradictory collector/renewal status. These were controlled inputs, not customer observations.
- **Still unverified:** Authenticated browser rendering and interactions, real user asset totals, deployed RLS/Realtime publication, authorization across two tenants, and end-to-end collector/stream/fallback delivery. The browser session inventory timed out, and the authenticated consistency check could not resolve the configured Supabase hostname. No actual tenant status was inferred from fixtures or health endpoints.

## Repair and acceptance order

1. **Protect the evidence and session boundaries, then make freshness truthful.** Verify deployed write grants and evidence producer roles. Delay an account A snapshot, stream and detail response while switching to account B; verify that no account A data renders. In the target environment exercise anonymous, entitled and unentitled requests. With the same signed-in session, test SSE normal delivery, first-frame timeout, silent stall, named error, token refresh and reconnect. Confirm usable REST fallback and degraded UI when the source is down.
2. **Fix evidence identity and lineage.** Establish tenant/asset, listener, certificate, operation and migration job keys plus a deduplication identity and distinct observation/read times. Verify one durable event appears once across the relevant modules; static scan evidence does not become a runtime observation; incomplete sources do not count as healthy or complete.
3. **Repair the decision models and workflows.** Compare an isolated tenant's TLS endpoints, event counts, certificate posture, cloud encryption, collector health, risk denominator and migration job outcome across all applicable pages. Use mixed pass/fail jobs, multiple ports and certificates, a revoked agent, missing and stale sources, and an incomplete scan. Verify that a TLS plan has the reviewed scope before approval and that it remains incomplete until the planned change is observed and validated.
4. **Run the final authenticated acceptance pass.** Start from the tenant's asset inventory and a trustworthy collector source, follow real scoped evidence through persistence and live delivery, then verify KPIs, tables, filters and drill-downs against the persisted counts, explicit windows and source health across all 17 pages. Record the source IDs and timestamps and test both an empty tenant and an account switch before treating the modules as operationally verified.
