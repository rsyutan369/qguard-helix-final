# Qguard Helix pricing and PayPal audit — 2026-11-16

**Release decision: do not sign off on live PayPal billing, revenue reporting, or withdrawals.** Live credentials can read eight active plans, but three monthly amounts disagree with the application catalog. The registered PayPal webhook is pointed at an unreachable project, and this audit found no verified sale, merchant settlement, or bank deposit. A healthy billing endpoint is insufficient evidence.

## Findings and recommended fixes

1. **P0 — Wrong live monthly prices.** New subscriptions and revisions reference a PayPal plan ID; the application never compares that plan's amount, currency, or cadence with the customer quote before checkout ([Edge create](../supabase/functions/billing/index.ts#L219), [Express create](../src/api-server/paypal.ts#L205)). Stop offering the three affected monthly checkouts until the deployed IDs are verified and prices corrected. Add a recurring provider/catalog check and fail closed on mismatched offers. Decide whether to reprice existing plans or create replacement plans for new buyers. PayPal says in-place pricing changes affect existing subscribers and may defer the new amount if their next cycle is within 10 days. Review actual merchant transactions for possible overcharges; these plan prices alone do not prove one occurred. [PayPal plan repricing rules](https://developer.paypal.com/subscriptions/change-price).
2. **P0 — Live webhook and reconciliation disagree with checkout.** The live webhook receiver and the hardcoded destination in [`paypal-webhook-setup.ts`](../tools/paypal-webhook-setup.ts#L21), [`billing-secrets-push.ts`](../tools/billing-secrets-push.ts#L20), and [`paypal-reconcile-schedule.sql`](../supabase/paypal-reconcile-schedule.sql#L28) point to the old project. Retarget the registered webhook for the confirmed live app, confirm the receiver uses the matching ID, and configure the scheduler in the verified project with its secret. Derive the project once and validate it before setup scripts make changes. Confirm an actual signed event reaches the ledger. Inspect live cron run history and reconciliation summaries, rather than inferring scheduler operation from health or an auth rejection. PayPal webhooks are scoped to the app that processed the payment. [PayPal webhook delivery and verification](https://developer.paypal.com/api/rest/webhooks/).
3. **P0 — Live revenue and admin SSE entry point unverified.** The repository expects Express for the dashboards and Supabase Edge for public PayPal checkout. In this audit the public site returned HTML to the API path and the configured API hostname did not resolve. Verify the intended dashboard origin, JSON proxy/CORS, service role project, and stream proxy behavior. Probe ticket issuance and the real `text/event-stream` response as owner, and verify a non-owner is denied. Keep the public Edge origin intentional; it is not the admin/revenue API.
4. **P1 — Valid money events can be acknowledged without financial records.** Edge sale processing returns when its subscription lookup has no row; that lookup also drops database errors. Refund processing returns for an unknown invoice. The webhook then marks the event processed, so an activation/sale race, a refund/sale race, or a database lookup error can lose an invoice or refund. Express has equivalent gaps. Reconciliation recovers completed sales only for a limited set of current agreements and does not repair missing refunds or reversals. Use durable pending and retry states for unresolved records, propagate DB errors, preserve historical agreement IDs, make ingestion idempotent by provider transaction or adjustment ID, and replay from provider evidence. [Sale](../supabase/functions/billing/index.ts#L373), [refund](../supabase/functions/billing/index.ts#L572), [webhook finalization](../supabase/functions/billing/index.ts#L815), [reconciliation](../supabase/functions/billing/index.ts#L935).
5. **P1 — Duplicate agreements and false cancellation are possible.** Checkout uses a timestamped PayPal request ID, so a repeat request can create another agreement. Activation cancels a superseded agreement on a best-effort basis and then overwrites the account's only agreement pointer; a failed cancellation can leave an older agreement billing. Edge treats every `UNPROCESSABLE_ENTITY` on cancellation as already cancelled; billing Settings Express accepts any HTTP 422 that way. Use a persisted checkout intent and stable request ID, track every agreement, serialize changes per account, and confirm remote state before reporting cancellation. The Express Settings flow also lacks the same Google Play guard as Edge and its return path does not use Edge confirmation. Route mutations through one implementation. PayPal plan revision requires buyer re-consent when the PayPal payment method is used and applies the new price at the next cycle; it does not automatically prorate, despite comments claiming proration. [Edge activation](../supabase/functions/billing/index.ts#L343), [Edge cancellation](../supabase/functions/billing/index.ts#L717), [Express Settings](../src/api-server/billing.ts#L1094), [PayPal plan revision](https://developer.paypal.com/docs/subscriptions/customize/revise-subscriptions/).
6. **P1 — `ACTIVE` is used as evidence of payment.** Checkout confirmation checks the signed-in user against PayPal's `custom_id` and resolves the provider plan server-side, which is a sound ownership check. It grants access on provider `ACTIVE` without requiring an initial completed sale. The payment refresh can set local status active merely because a next billing time exists; reconciliation can also turn local `past_due` into active from lifecycle status alone. Define grace explicitly; use actual successful or failed payment evidence and monotonic provider state for paid-through access. Include the billing cycle and provider plan ID in drift detection: the Edge reconciliation predicate only compares tier, status and next billing time. [Confirmation](../supabase/functions/billing/index.ts#L702), [renewal refresh](../supabase/functions/billing/index.ts#L429), [drift detection](../supabase/functions/billing/logic.ts#L489).
7. **P1 — Dashboard revenue is not a settlement figure.** Net Revenue is recorded gross less recorded refunds; PayPal invoice rows do not store fees or settlement, and MRR falls back to catalog prices when no actual recurring amount is saved. Thus a charge at the mismatched price and a lower dashboard MRR can both appear to pass the dashboards' internal consistency checks. Multiple partial refunds accumulate on one invoice, and the current model books their combined amount at the latest refund time, which moves earlier refunds between periods. Ingest each charge/refund with its own timestamp and normalized currency, store effective renewal terms, and reconcile against PayPal transaction and balance reports or statement imports. Label gross, refunds, fees, settled proceeds and transfers separately. Business profit additionally requires expense data. [Invoice mapping](../supabase/functions/billing/logic.ts#L224), [refund mapping](../supabase/functions/billing/logic.ts#L393), [MRR](../src/lib/billing/revenue-model.ts#L242), [revenue windows](../src/lib/billing/revenue-model.ts#L917), [PayPal balance reporting](https://developer.paypal.com/reports/financial-reports/balance-report/).
8. **P1 — Billing history can be removed or orphaned on account deletion.** Admin protects managed subscriptions only when the local status grants access. A past-due or suspended agreement may still be managed remotely; verify provider terminal state before deletion. The base invoices schema also links invoices to auth users with `ON DELETE CASCADE`, so account removal can erase source transactions used for reports. Confirm the live constraint, retain financial records independently of profile deletion, and minimize retained personal data. [Admin guard](../src/api-server/admin.ts#L1443), [invoice schema](../supabase/billing-subscription-schema.sql#L94).

## Collection and withdrawal acceptance

1. Confirm the PayPal Business owner recognizes the exact live REST app and can see the intended eight plans and merchant activity. Verify the destination bank or eligible transfer method, settlement currency, available balance, fees and holds in PayPal. The app does not move merchant funds to the bank. [PayPal Wallet transfer instructions](https://www.paypal.com/ph/cshelp/article/how-do-i-withdraw-money-from-my-paypal-account-help394).
2. After correcting routing and prices, run a sandbox sequence covering checkout, failed collection/recovery, renewal, same-tier monthly/yearly revision, cancellation, out-of-order delivery and replay, partial refunds across reporting periods, and reversal without ever fabricating a paid production record.
3. With the merchant owner's authorization, run one live Starter monthly checkout with a separate eligible buyer. Confirm the actual $1 USD sale, correct merchant/payee, paid fee and settled net, one invoice, one paid entitlement, and corresponding changes in Customer Billing, Admin and Revenue Intelligence. Reconnect each stream and confirm it reloads the same current state. Refund/cancel the test as approved.
4. Have the merchant owner initiate an eligible transfer from PayPal and confirm the actual bank receipt against the PayPal transfer record. A payment credited to PayPal, an available PayPal balance, and a completed bank transfer are separate milestones.
