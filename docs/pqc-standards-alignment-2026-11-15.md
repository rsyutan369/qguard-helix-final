# Qguard Helix PQC standards alignment review

Review date: November 15, 2026. Scope: the public homepage and Quantum Simulation Range; standards guidance used by Compliance, Estate Intelligence, Migration Sandbox, Live Migration Ops, Encryption Monitoring, Public Scan, Sophia, and key and certificate records. Review of workspace code and isolated tests, not an assessment of a deployed tenant or a product certification.

**Published site finding:** The live [qguardhelix.com](https://qguardhelix.com/) serves a separate under-construction page. Its terminal displays “NIST FIPS Standards Compliance 100%” and “Entropy 100%” without supporting evidence, and its transport section promises upgrades without disruption. Remove those claims or identify the terminal as an illustration and replace its metrics with plain capability descriptions. The corrected public build in this workspace has not been published; the current maintenance page's source was not found here.

## Source and applicability

| Primary source | What the platform should infer |
| --- | --- |
| [Final NIST IR 8547](https://nvlpubs.nist.gov/nistpubs/ir/2026/NIST.IR.8547.pdf), §§3.2.1, 4.1–4.2 | NIST will deprecate the covered quantum-vulnerable public-key schemes after 2030 and disallow their use under NIST standards and guidance after 2035. Both stages apply across the covered key sizes. Earlier system-specific requirements still apply. This schedule does not forecast when a quantum computer will exist. No general transition away from AES-128, AES-192, or AES-256 follows from the public-key schedule. |
| [NCCoE Migration to Post-Quantum Cryptography](https://www.nccoe.nist.gov/applied-cryptography/migration-to-pqc) | Build inventory and use it to prioritize risk; test interoperability and performance before production rollout. NCCoE's project guidance and preliminary SP 1800-38 volumes are not an accreditation or compliance framework. |
| [NIST's first finalized PQC standards](https://www.nist.gov/news-events/news/2024/08/nist-releases-first-3-finalized-post-quantum-encryption-standards) | FIPS 203 defines ML-KEM for key establishment; FIPS 204 defines ML-DSA and FIPS 205 defines SLH-DSA for signatures. A detected algorithm label, passing library smoke test, or supported parameter set does not establish application conformance or [FIPS 140 module validation](https://csrc.nist.gov/Projects/Cryptographic-Module-Validation-Program/Validated-Modules). |
| [Executive Order 14412](https://www.whitehouse.gov/presidential-actions/2026/06/securing-the-nation-against-advanced-cryptographic-attacks/), §§4 and 6 | Agencies designate a migration lead. Federal high value assets and high impact systems in §4(b), excluding National Security Systems, are due for PQC key establishment by December 31, 2030 and PQC signatures by December 31, 2031. A federal designation is not the same as a high Qguard risk score. Section 6(c) directs a **proposed** FAR rule; do not derive a blanket contractor obligation from the order. |
| [OMB M-26-15](https://www.whitehouse.gov/wp-content/uploads/2026/06/M-26-15-Execution-of-the-Migration-to-Post-Quantum-Cryptography.pdf), §3 and Appendices A/B | Federal agencies outside the memo's National Security Systems exclusion must submit a plan within 120 days of issuance and prioritize risk, including highly sensitive systems and particularly exposed systems. Support TLS 1.3 or a successor by January 2, 2030; a TLS version observation does not prove an ML-KEM negotiation. Hybrid use is risk- and implementation-dependent. |

OMB §3(D) describes five phases through 2035. Appendix B §2 calls for risk-based priorities, milestones, TLS testing and deployment, inventory methods, crypto agility, third-party coordination, resource estimates, transition risk management and governance roles. Appendix B refers to “three” phases even though §3(D) enumerates five; Qguard's reference uses the five phases enumerated in the body and points readers to the memo. NSA [CNSA 2.0](https://www.nsa.gov/Resources/CNSA-Suite/) has a separate National Security Systems scope. Do not apply it to every federal or commercial tenant.

## Remaining work before an agency or validation claim

1. **Verify affected consumers of retired issuance routes.** Identify any integrations that used `POST /api/v1/keys`, `POST /api/v1/pki`, or corresponding QRNG stream actions. Check their deployed keys and certificates against the owning provider; treat the legacy labels, fingerprints and quality values as unverified. The review did not inspect live customer records or alter persisted history.
2. **Add an explicit federal applicability profile and plan package.** Capture an approved HVA designation, FIPS 199 impact, NSS exclusion, mission sensitivity and owners. Track the separate key establishment, signature and TLS milestones per asset. Build an Appendix B plan export including vendor responsibilities, funding, staffing, exceptions and approval evidence. The current catalog provides references and evidence navigation; it does not submit the plan or attest to agency compliance.
3. **Verify deployed cryptography with independent evidence.** For every relevant provider/version, record algorithm and parameter set, actual protocol negotiation and fallback rules, authentication or signature validation, client and server interoperability, and CMVP certificate number, operating environment and approved mode when module validation is required. Local round-trip and paired-stream lab checks do not replace this.
4. **Review adjacent entropy previews and non-primary sources before making broader claims.** Other QRNG-based service screens and reference API pages still contain legacy simulated status, quality values or certification wording outside the issuance corrections. Treat them as unverified until the actual entropy provider and production path are validated. Check NSS, international and sector-specific controls separately for each customer's scope.

Local verification included the full and public builds; governance, estate, QKMS, Sophia, simulation, and sandbox regressions; explicit checks that issuance stops without provider evidence; and isolated server rendering of the landing page, simulation page, and issuance views. The local lab exercised ML-KEM, ML-DSA, SLH-DSA and paired TLS 1.3 handshakes. The public bundle passed its platform-isolation checks; configure the public API origin before releasing it with Public Scan and Request Demo enabled.

No production deployment or production tenant assessment is part of this review. The local browser could not reach the loopback preview; the render checks do not establish interactive behavior in a signed-in production dashboard.
