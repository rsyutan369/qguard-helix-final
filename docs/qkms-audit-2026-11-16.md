# QKMS technical audit — 16 November 2026

Scope: the seven locally requested QKMS routes, following [the audit guide](../Qguard_Wiki/QKMS_Audit). This is a source and schema review, with offline model checks and isolated local HTTP/browser smoke tests. It is not an assessment of a deployed federal system or an independent cryptographic validation.

## Executive assessment

**QKMS is a cryptographic metadata registry, discovery dashboard, and work-order tracker. It is not a custody or cryptographic execution service.** All seven dashboard views are backed by Express and share a Supabase-derived model. The supplied code did not support the earlier implication that closing a work order verifies rotation, creates key material, updates dependent services, or validates a migration. That claim has been removed from the model and UI. No workspace, provider account, or customer key was changed during verification.

Source review found execution, authorization, evidence quality and deployment gaps that still preclude production sign-off as an enterprise KMS. The most consequential remaining gaps are provider-bound execution/validation, enforcement of roles and separation of duties, and authoritative transactional audit. Positive readiness and risk observations are scope-limited indicators; they are not certification or proof of controls.

## Data path and per-page conclusions

`src/App.tsx` mounts all seven page wrappers under the authenticated dashboard. Each wrapper loads a component in [the QKMS UI](../src/app/dashboard/_components/qkms) and a named wrapper in [use-qkms.ts](../src/hooks/use-qkms.ts). Initial JSON and SSE both reach [qkms-dashboard.ts](../src/api-server/qkms-dashboard.ts) under `/api/v1/dashboard/qkms`; `/api/qkms` is a legacy mount. The Express subscription gateway precedes both mounts. GET `/:mode`, SSE `/stream?mode=...`, GET `/keys`, GET `/keys/:id`, GET `/export`, and the writes use the same user-bound model and RLS-aware Supabase client. Subscriptions are product entitlements, not security duty roles.

### Supabase and event evidence

- Primary QKMS tables: `qkms_keys` (canonical key reference and metadata), `qkms_key_versions` (tenant + key reference + version), `qkms_policies`, `qkms_rotation_jobs`, `qkms_audit_events`, `qkms_storage_backends`. Base and extension SQL are [qkms-lifecycle-schema.sql](../supabase/qkms-lifecycle-schema.sql) and [qkms-command-center-schema.sql](../supabase/qkms-command-center-schema.sql). Consumer joins are mostly by text reference, not DB foreign keys. Deployed catalog, grants, policies, indexes, duplicates, and publication membership were not inspected.
- Estate sources: `assets`, `generated_keys`, `crypto_inventory`, `certificates`, `scanner_evidence`, `runtime_crypto_events`, `migration_jobs`. Supporting evidence: `compliance_evidence`, `vault_audit_logs`, `qrng_events`, `scanner_agents`, `connector_accounts`, `agent_heartbeats`, `pqc_scan_sessions`. Source pulls now request counts and ordered ranges because the Supabase response limit can be less than the application limit. A core query failure withholds the view; optional failures and truncated sources are identified. Writes during pagination can still make the refresh non-atomic. Scale-test exact counts and consider a single database snapshot/read model with explicit retention and window bounds.
- One authenticated fetch stream per mounted page, not four EventSources; HTTP bearer header only, a projected `qkms` frame, `qkms-error` on read failure, and a comment heartbeat (25 s). The server polls the model every 10 s with a 15 s in-process cache; own writes invalidate that cache and wake same-process streams. Supabase Postgres Changes nudges a debounced refresh on listed tables; the stream rebuild covers remaining inputs. Streams close on response close or token expiry; the browser validates the content type/mode, detects stalled transport, orders frames by timestamp, reconnects with backoff, and stops labeling errored data live. User/token scoping prevents cross-project cache reuse. This architecture uses snapshots, not replayable event delivery or a durable cross-node bus. Realtime publication, signed-in frames, SSE proxy buffering, reconnect under JWT refresh and kill-switch behavior were not proven on a deployed instance.
- JSON and SSE both use `projectView`. The offline revocation fixture checks all seven projections plus inventory lifecycle and removal from the rotation queue. Browser resync of a saved change, two distinct users under RLS, simultaneous write and actual Supabase row changes remain acceptance tests.

### Interpret the measurements

- **Readiness:** equal per-key coverage in the operational asymmetric decision scope, with unknown algorithms included and terminal/unusable date statuses excluded from headline readiness. The numerator requires a source observation or generated record plus usable PQC algorithm classification. Declaration alone does not count. Each readiness band uses its own applicable population; no applicable records return null. The gate is a separate set of prechecks with blockers and warnings; its score is pass count over evaluated checks, not a percent of migrations completed. Snapshot timestamp is `generatedAt`; gate timestamp is `evaluatedAt`. This report documents the audit revision of the method; durable scoring version/evidence lineage and per-assessment history are future requirements.
- **Risk:** the [risk engine](../src/lib/qkms/risk.ts) aggregates bounded grades for algorithm (22), quantum exposure (20), lifecycle (15), rotation (14), ownership/governance (11), custody (10), and exposure (8). Severity floors apply to verified rule conditions as defined in code; confidence measures weighted evidence coverage, not model probability. Scores need the evidence refs and confidence shown in the drawer. Asset context and dependency hints inform triage; they do not replace threat likelihood, business impact and data confidentiality lifetime. No HNDL event or CRQC deadline follows from a vulnerable algorithm.
- **Governance and custody:** a pass compares available metadata against enabled policy rules. Unknown exportability, algorithm, missing dates, and asserted HSM proof are treated conservatively. A generated-key row without explicit custody no longer defaults to the platform vault. Defaults and policy day values are product/tenant thresholds; NIST does not impose a single symmetric, signature and establishment cryptoperiod. Report timestamps, caps, and sources travel with the output. Ordinary QKMS views do not select raw generated key fields or forward arbitrary audit before/after JSON; free-text metadata remains an input trust boundary. Formal custody, entropy and validation claims require provider/module evidence.

## Remediation and remaining risk

1. **High — Provider authority.** Removed false validation, key version and rotation success claims. Enable actual rotation/revocation/destruction only after implementing an authorized provider integration, independent provider events, dependency health checks, previous-version recovery and sequencing. Reconcile historical rows using independent records; no automated historical rewrite was made.
2. **High — Authorization and audit integrity.** The existing tenancy primitive is user ID, not an organization membership/role. The API has no separation between requester, approver, executor and validator. Tables governed by broad authenticated RLS can still accept same-user metadata writes where grants permit, and audit insert is not authoritative proof of actor or outcome. A write and audit insert still span requests; the response now discloses an audit failure. Enforce roles at both API and DB, route changes through scoped atomic transactions, derive actor from session, use an append-only outbox with restricted grants and audit shipping, and require independent approval where applicable.
3. **High — Data quality.** Fixed silent empty core reads, visible source coverage, scope of authorization caches, known incomplete readiness decisions, misclassified PQC variants and hybrids, rotation audit provenance, selected lifecycle precedence, ambiguous runtime attribution and policy no-op writes. Remaining: per-provider provenance, canonical identity collisions (including hash-based IDs and fingerprint provenance), pre-post snapshot pinning, exhaustive schema compatibility, policy input validation and complete custody/usage proofs. A local report is not estate completeness evidence.
4. **Medium — Real-time reliability.** Fixed stale errors, client transport watchdog and reconnect, response-level close cleanup, overlapped pushes, and refresh of detail/paginated data even when summary values are unchanged. Validate signed-in two-tab updates, connection aborts, proxy idle timeout, no-cache headers, token refresh, and direct table writes on the intended topology. No durable cross-replica delivery guarantee is offered.
5. **Database change staged in the workspace only.** [qkms-audit-hardening.sql](../supabase/qkms-audit-hardening.sql) tightens the named QKMS RLS predicates to the same two identifiers as the API and places a unique index on open canonical work orders. Apply after the base/extension to an isolated Supabase project, inspect existing duplicate/legacy rows and additional permissive grants/policies, then verify two-user isolation and concurrent requests before promotion. The migration intentionally fails on duplicate canonical open orders rather than silently deleting data.
